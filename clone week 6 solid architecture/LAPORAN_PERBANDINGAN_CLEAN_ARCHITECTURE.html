Laporan Perbandingan Arsitektur: Week 6 Awal (Folder JS) vs Clean Architecture (Folder Clone)

1. Ringkasan Eksekutif

Laporan ini menyajikan analisis komparatif menyeluruh antara implementasi awal Week 6 (Authentication, Security & FCM) yang berada di folder JS dengan implementasi Clean Architecture yang telah diterapkan pada folder clone/06-week-6-authentication-security-fcm-clone.

Refaktorisasi ini didasarkan pada materi kuliah mengenai Clean Architecture dan Prinsip SOLID dalam Flutter, dengan aturan kunci:

  • Dependency Rule: Dependensi hanya mengarah ke dalam (Presentation → Domain ← Data).
  • Domain Purity: Domain murni Dart tanpa dependensi ke Flutter, Dio, SQLite, atau Firebase.
  • Separation of Concerns: Widget UI tidak boleh mengimpor atau memanggil HTTP client / local storage secara langsung.

A. Pemanggilan Endpoint Terlindungi (/me) di Dashboard

❌ Sebelum (Folder JS - Widget memanggil Dio langsung): 
// lib/pages/home_page.dart
Future<void> _testProtectedApi() async {
  setState(() => _isTestingApi = true);
  try {
    final dio = ref.read(apiClientProvider); // <-- Panggil Dio langsung dari Widget
    final response = await dio.get('/me');   // <-- HTTP mentah di dalam UI!
    setState(() {
      _apiTestResult = 'HTTP ${response.statusCode}: ${response.data}';
      _isTestingApi = false;
    });
  } catch (e) {
    setState(() => _apiTestResult = 'Gagal: $e');
  }
}
✅ Sesudah (Folder Clone - Widget memanggil Domain UseCase): 
// lib/presentation/pages/home_page.dart
Future<void> _testProtectedApi() async {
  setState(() => _isTestingApi = true);
  try {
    // Memanggil UseCase domain: Bebas dari import dio, http, atau json parsing

      _apiTestResult = 'Profil Diterima dari UseCase:\n'

    });

  }

5. Evaluasi Berdasarkan 5 Prinsip SOLID

Prinsip Week 6 Awal di JS Hasil Refactoring di Clone
Single Responsibility (SRP) home_page.dart (>900 baris) mencampur HTTP, state notifikasi, dan UI widget. UI hanya menggambar tampilan; UseCase mengurus alur bisnis; DataSource mengurus I/O.
Open/Closed (OCP) Menambah tipe storage atau client baru mengharuskan mengubah seluruh widget. Dapat menambah DataSource baru tanpa menyentuh Domain UseCase atau Widget.
Liskov Substitution (LSP) Sulit membuat repository tiruan karena tidak ada kontrak interface seragam. Semua implementasi dan fake repository mematuhi kontrak antarmuka Domain yang sama.
Interface Segregation (ISP) Satu kelas raksasa menampung semua fungsi token dan HTTP tanpa kontrak terpisah. Kontrak dipisah secara modular: AuthRepository dan TokenRepository mandiri.
Dependency Inversion (DIP) Widget dan Notifier bergantung langsung pada implementasi konkrit (Dio & SecureStorage). Presentation hanya bergantung pada abstraksi Use Case dan Repository Interface.
